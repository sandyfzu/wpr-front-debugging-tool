#### Receipt — 2026-10-17

- The store stays exactly as .3 left it (`state/search.ts`: raw streaming, revision, cursor/wrap over the reported count) — the page side is one composable, `entrypoints/panel/pages/current-match.ts`: `createCurrentMatch(search, matchingRows)` hands each list page `current` (the cursor's row) and `request` (the find's scroll event). Reporting runs in a first-run effect: blank/whitespace queries acknowledge 0, a live query reports its rendered set, a remount under an active query (retry/refresh lifecycle) re-reports at once; dispose clears **only the count it was the last to report**, so a disposed page can never erase a successor's newer claim (on a route change the outgoing cleanup runs before the shell's reset effect — verified flush order on the installed Solid — and the reset zeroes the store anyway).
- The two accessors deliberately track different sets: `current` tracks the match set too, so a refresh shrink/chip change re-derives it and an out-of-range cursor names no row (the store's wrap math snaps the stale cursor on the next step); `request` tracks only find events (committed query, next/previous) and reads the set size untracked — a fresh object per event, so a new commit re-fires the scroll even when it lands on the same row index, while geometry-only changes retain the request identity and never scroll (refresh/user scroll must not snap).
