# P21: WP Rocket simulation on sites without the feature

## TLDR

Owner idea (2026-10-21): simulate a WP Rocket optimization on a page where it is off, riding P10's before-parse interception (Chromium `chrome.debugger` + CDP `Fetch`, Firefox `filterResponseData`), then try exclusions on top. Use case: a customer reports a Delay JS problem, Delay JS is off when support visits, no credentials. Not P10's rejected G-3 "simulation fallback" (an approximation _instead of_ interception); P21 rides the interception.

**P21A decided 2026-10-28** ([record](#p21a-decision-record-2026-10-28)); **every owner gate decided the same day** ([gates](#owner-gates-decided-2026-10-28)). Scope: Delay JS, then Defer JS (P21L), then Lazyload (P21M), registry open for later features. Delay JS is reproduced byte-for-byte from WP Rocket's own passes (live receipt: real plugin Delay pass on the site's Delay-off page = its Delay-on page, minus the generator meta), for the owner-pinned supported versions — the latest stable WP Rocket + the previous minor's latest patch, today **3.24 + 3.23.5.1** (P21V; at each new minor the owner decides whether the oldest stays — SG-9). Simulation = a pre-exclusion step in the one P10 pipeline whose output then composes with exclusions exactly as a real Delay-on page does; the Delay lane's switch becomes **As served · Simulated · Disabled**, set from the page's real Delay state; its own extension meta (never a fake `data-wpr-features` token), an authority for detection only once the background verifies it, so simulated Delay never counts as served nor as "WP Rocket present"; identity where WP Rocket already delays; "Simulated" words on every surface; page CSP reported, never bypassed. WP Rocket's runtime is injected verbatim from the packaged asset only (never fetched code; each supported version's runtime bundled, deduplicated by content hash); WP Rocket's Delay exclusion list ships bundled per version and is superseded by a strictly validated latest list fetched from WP Media's official endpoint (data only — the Known Conflicts seed + live pattern; no license sent). Allowed on sites without WP Rocket; admin/login screens warn, never block (owner); logged-in renders allowed (plan). P21B–P21N + P21V + P21.1 below; **P21 complete (owner manual arms pending)** 2026-10-30: every slice (B–N, V, P21.1, L, M) done; the owner's manual arms are the [P21.1 checklist](#p211--suites-and-manual-arms). Gate ids are `SG-n` (simulation gates), distinct from P10's G-1…G-5.

**Depends:** P10 (pipeline seam, overlay, session), P10K (row semantics + PHP parity harness), P14.5D0 (served script URL; plan: before P21I, which reuses its helper). **Train slot:** before release (owner 2026-10-22), closed before P8, gated by P15; P12 is merged (`develop` 6542201, this branch e617ee7), so no slice waits on it ([SG-10](#owner-gates-decided-2026-10-28)). **Q6 — Placement (SG-2 decided).**

- Answer: the Delay JS lane's "Disable feature" switch (`entrypoints/exclusion-overlay.content/exclusions/lane.tsx:409-425`) becomes **one 3-option segmented control: As served · Simulated · Disabled** (Delay lane only; the Defer and ALR lanes keep their switch until their simulation phase — Defer in P21L). **Q7 — Per-browser feasibility and CSP (SG-3 decided).**

- Facts: the pipeline does nothing with CSP today (no hits in `lib/exclusion-session`, `lib/exclusion-builder`, `entrypoints/background`); Chromium fulfils with original headers minus framing/cookie/speculation headers (`lib/exclusion-session/chromium/paused-request.ts:70-85`); Firefox rewrites the body in place, headers untouched (`entrypoints/background/stream-filter-backend.ts`). The runtime is **inline**, recreates delayed scripts (copying the original's `nonce`), uses `new Function("event", …)` (needs `'unsafe-eval'`) and `data:text/javascript` script URLs (needs `data:` in the script directive), with its own `securitypolicyviolation` fallback for `script-src-elem` (`sessionStorage.rocketCSPIssue`). CSP3 §3.3: a `<meta http-equiv>` policy is "not applied to content which precedes" it — the runtime sits right after `<head>`, before most metas, so a meta policy binds the runtime's later work, not the runtime element. CDP has `Page.setBypassCSP`, `Fetch.fulfillRequest.responseHeaders`. MDN (`webRequest.onHeadersReceived`): extensions' CSP header values are combined; a conflict between two extensions resolves to the stricter policy; "an extension may remove the original CSP header". BCD: MAIN-world scripting Chrome 95+/Firefox 128+ (below floors 145/150).
- Answer (owner: "do what WP Rocket does" — this is it): inject inline exactly where WP Rocket does; never bypass; the page's CSP applies as it would live. The only addition is naming the cause. A pure CSP evaluator over header policies (Chromium paused headers; Firefox `responseHeaders` captured in a Firefox-only module) + meta policies with their offset decides: runtime element blocked (inline disallowed by a header policy, or by a meta policy preceding the insertion point) ⇒ `csp-blocked`, step = identity: "This page's Content Security Policy blocks inline scripts — WP Rocket's Delay JS would be blocked the same way."; runtime allowed but some of its work blocked ⇒ `simulated` with `cspLimits` naming each, per browser and **per delayed script** (P21B — a nonce is per element): `eval` = `'unsafe-eval'` absent (`on…` handlers of elements parsed after the runtime throw `EvalError`); `inline` = at least one delayed inline script fails. Firefox recreates every delayed script (nonce copied): an inline one runs ⇔ its nonce matches, or `'strict-dynamic'` is present (the allowed runtime inserts it), or `'unsafe-inline'` is in effect. Chromium first points it at a `data:` URL in place: it loads ⇔ `data:` allowed, or its nonce matches, or `'strict-dynamic'`; else a `script-src-elem` `data` violation sets `sessionStorage.rocketCSPIssue` and the runtime recreates it (and every later delayed script in the tab session) as inline, allowed as on Firefox — it fails only when both paths are disallowed. `data` = Chromium only: a delayed inline script's `data:` load blocked but its recreated inline allowed — nothing fails, the fallback logs a violation (informational). Copy: "This page's Content Security Policy blocks <eval / inline scripts> — WP Rocket's Delay JS hits the same limit live; delayed scripts that need it fail here as they would on the site."; `data` alone: "This page's Content Security Policy blocks data: scripts — WP Rocket's Delay JS falls back to inline scripts, as it would live." (exact reproduction, not a half-working extension feature). **No nonce reuse** (WP Rocket adds none). Same path on both browsers; Chromium serves a fulfilled copy (neutral security, TTFB includes the pause) — timing tools must label it.
- **Verified (P21B-CSP, 2026-10-28; CFT 156.0.8078.4 + Firefox 159.0, headless; table in [P21B](#p21b--probespike-csp-runtime-execution-logged-in-admin-screens-latest-list-response-scratch-only)):** page CSP applies to fulfilled copies exactly as served — 16 policies × direct / Playwright-CDP fulfil / `chrome.debugger` fulfil (Chromium) and direct / `filterResponseData` (Firefox), identical per browser, plus 8 nonce / `'strict-dynamic'` / precedence pages; the runtime runs on a fulfilled copy (6/6 delayed scripts `executed`, `?fdt-delay=1` error only after interaction); a `<meta>` policy before the insertion point blocks the runtime, after it binds only later work (eval, `data:`, recreated inline); `Page.setBypassCSP` is accepted by `chrome.debugger` and effective (still rejected below). Injections under `script-src 'self'`: MAIN-world `executeScript` runs, its eval and appended inline are blocked (both browsers), its `data:` script blocked (Chromium; Firefox untested); `addScriptToEvaluateOnNewDocument` (needs `Page.enable`) runs, its own synchronous eval is **allowed**, its appended inline blocked (`data:` and later eval untested) — no established advantage for the runtime's inline-script work, so inline stays (SG-3). Receipted on Chromium: `script-src-elem` > `script-src` for elements, `script-src` > `default-src` for eval, `'unsafe-inline'` ignored beside a hash or a nonce; both browsers: multiple policies all apply, report-only never blocks (but its `data:` report flips Chromium's runtime to the inline fallback), nonce-only policies block the runtime (no nonce added), `'strict-dynamic'` + a hashed runtime lets delayed scripts run with or without a nonce. Spec facts, not receipted: the same precedence on Firefox; `'unsafe-inline'` ignored beside a lone `'strict-dynamic'`. `sessionStorage.rocketCSPIssue` survives same-origin navigations in a tab: after an earlier page flipped it, Chromium recreates from the start, so a policy allowing `data:` but not inline then fails inline scripts a per-document evaluation would pass (receipted once). `data-rocket-status="executed"` is set on recreated scripts CSP blocked — never proof of execution. Headers: Chromium paused `responseHeaders` keep repeated CSP lines as separate entries and the Report-Only header under its own name (compare names case-insensitively); Firefox `onHeadersReceived` joins repeated lines with `, ` (split policies on commas) and needs port-less match patterns (a port in manifest patterns grants nothing (`executeScript`: 'Missing host permission'; content script not injected); in `webRequest` filter URLs it misses silently).
- Rejected: `setBypassCSP`/header removal (the page then runs what the real site blocks); hash added to the header (header surgery per document, merges only tighten across extensions, deviates from WP Rocket); nonce reuse (deviates from WP Rocket); MAIN-world/`addScriptToEvaluateOnNewDocument` runtime (timing/frame drift, all-frames guard, static content script costs every page) — only if P21B-CSP proves inline unworkable, and then back to the owner; treating partial blocks as `csp-blocked` (hides the very failure the site would show live).

**Q8 — Performance budgets.**
