## TL;DR

Port the **entire** legacy extension — 8 entrypoint surfaces, 2 content scripts (isolated + MAIN world), a 13-check WP Rocket detection engine, Known Conflicts DB syncing, Side-by-Side compare, undefined-references finder, WP Rocket Diagnoser support, popup option-toggling, options page, context menus, devtools sidebar pane, and the Exclusion Builder — plus the feature set of the second behavioral baseline, [`wp-media/wpr-inspector`](https://github.com/wp-media/wpr-inspector) @ v4.1.1 (§9 — meta-tag-driven detection coverage, the on-page inspector strip, the RUCSS live tester, and the runtime analysis tools), across **34 ordered phases** (P0, P1, P1.1, P2–P4, P4.1–P4.3 browser-test infra + retro suites, P16 — the comparison-tooling phase: Side-by-Side scroll sync + the overlay-scoped SBS mobile comparison (05g), P5–P14 each with its own browser-suite sub-phase `X.1` (P5 itself ships as the sub-phases **P5A–P5J** (P5J scheduled in the release train's terminal slot — 06d) — its doc's §Sub-phase structure), P14.5, P14.6 external-site track, P15) — with **P7 (Diagnoser) deferred to the last implementation slot** (gated on the rebuilt Diagnoser plugin) and **P17 (SBS panel home)** decision-gated optional.

Ordering logic: **foundations → shared contracts/engine → data producers (background, content scripts) → browser-test infrastructure + retro suites (P4.1–P4.3, the next thing implemented) → data consumers (devtools panel, popup, options) → independent satellite (exclusion builder) → hardening/release.** Each phase is independently verifiable and ends with all quality gates green; every feature phase also gets a browser-suite sub-phase (`X.1`) that runs its browser-observable checklist through the local Playwright harness + dockerized WP site (§3's Browser-test track). P1.1 is an engine-correctness insert right after P1: the measurement beacon is shared by four WP Rocket Priority-Elements features (Optimize critical images, Automatic Lazy Rendering, Preload fonts, Preconnect to external domains — verified against the plugin source), so the beacon gets its own detection row and each feature is detected independently, before any consumer (P3 data hub, P6 cards) can render the beacon-mislabeled verdict.

**P6G execution detail (2026-10-16):** the final P6 page-polish block is divided into **P6G.1–P6G.10**, with module boundaries, dependencies, parallelism, tests, and acceptance in [07c](./07c-phase-6g-search-and-polish.md). Next/previous search results are one complete feature slice (P6G.5); the preceding shared-list and keyboard pieces keep that implementation local. This decomposition leaves the release ordering and P6.1 close-out unchanged.

Non-negotiable direction on every ported feature:

- **Faster & lighter** — verified legacy baselines (see §1) become hard budgets: e.g. isolated content script ≤ 60 KB raw (legacy 119 KB), panel JS ≤ 600 KB hard / ~350 KB target (legacy ~1.6 MB). Fine-grained SolidJS reactivity, single-pass detection, lazy/heavy-dep loading, no animation/router/toast libraries.
- **More secure** — runtime validation at every boundary (messages, storage, page DOM data), least-privilege manifest with documented `host_permissions` (legacy had none — see §1), no untrusted string → HTML anywhere, capped error-word capture.
- **More reliable** — fixes for real legacy bugs found during this audit (stuck single-flight flag in the KC updater, hook-order violation in DiagnoserPage, unresolved Promise when a page has no scripts, wrong `window.open` arg, dead search next/prev protocol, dead 50-error cap, mislabeled "Lazyload" badge on the Preloaded page — all listed in §6).
- **Better UI, categorically** — a purpose-built Kobalte + Tailwind v4 design system (dark-first, devtools-compact density, both palettes behind a three-way appearance setting — system/dark/light — on every surface, keyboard-complete, `prefers-reduced-motion`-aware) replacing legacy's shadcn/framer-motion look; virtualized resource lists; real JSON tree instead of syntax-highlighted dumps; inline regex validation in the Exclusion Builder; skeleton loaders; empty/error states everywhere.
- **Extends where it pays for itself** — toolbar action badge (WPR presence/cached at a glance per tab), copyable markdown support report + detections summary strip, response-headers viewer, undefined-references → exclusion-builder bridge, Elements-pane rocket-attribute inventory, KC-DB freshness UI, CI on every PR. Each has an owning phase and a verification hook (§8).

Estimated flow: P0–P1.1 foundations (1 unit), P2–P4 producers (1–2 units), {P4.1 harness ∥ P4.2 local-WP site} + P4.3 retro suites (1–2 units — ✅ done, 2026-10-09; records 05b–05d), P16 SBS scroll sync + mobile simulation + its two presentation extensions (owner-committed 2026-10-08 — Feature A shipped 2026-10-11, the comparison's P16.2 refinement shipped 2026-10-12, its device tag (05h) and desktop width (05i) shipped the same day in the follow-up round; records 05e/05g/05h/05i), P5 ✅ the devtools panel (shipped through P5I, 2026-10-13 — P5J alone remains, holding the release train's terminal slot; records 06/06a/06b) and P6 the panel pages (executed as sub-phases P6A–P6G, split committed 2026-10-14 — 07 §Sub-phase structure) with their P5.1/P6.1 suites (P7 — Diagnoser — executes last, gated on the rebuilt Diagnoser plugin), P8–P10 satellites (1–2 units) with P8.1–P10.1 suites, P11–P14 second-baseline integration (2 units; see §3) with P11.1–P14.1 suites, P14.5 feature coverage & tooling (1–2 units; §10), P14.6 external-site track (decision-gated), P5J panel header/nav redesign (owner decision 2026-10-13 — the release train's last implementation phase; record 06d), P15 release (1 unit). Phases P2/P3/P4 ran as the implemented set, followed by P4.1∥P4.2, P4.3 and P16 (all shipped); **P6 — the panel pages — is the next implementation block**, executed as sub-phases P6A–P6G (07 §Sub-phase structure) and parallelizable with P8/P9 (P5 shipped through P5I, 2026-10-13; P5J keeps its release-train slot after P7, before P15); P8–P10 in parallel after their stated deps; P11–P14 after their own (each phase doc states them).

### 1.2 Legacy manifest (verified from built `.output/chrome-mv3/manifest.json` — built from v2.2.5 source; the on-disk 2.2.3/2.2.4 zips are stale)

- `permissions: ["contextMenus", "webRequest", "storage", "alarms", "tabs"]`, `minimum_chrome_version: "120"`.
- **No `host_permissions` at all** — despite `webRequest` listeners for `http(s)://*/*`. Per Chrome's webRequest docs, listeners only receive events for URLs covered by host permissions, so header capture likely only works incidentally or not at all; the port declares `host_permissions: ["http://*/*", "https://*/*"]` explicitly (P2 verifies and documents the difference).
- Content scripts: both `document_start`, matches `http://*/* + https://*/*`, MAIN-world variant declared with `world: "MAIN"`.

## 2. Architecture (target data flow)

```
                         ┌────────────────────────────── background (SW) ─────────────────────────────┐
                         │  headers: webRequest.onResponseStarted → per-tab cache (cap, onRemoved GC) │
                         │  KC DB: alarms(60m) + onStartup + manual → fetch → validate → local:storage│
                         │  context menus → messages to CS(tabId) / open exclusion-builder tab        │
                         └──────▲──────────────────────────────────────────────────▲───────────────────┘
                                │ runtime messaging                                │
┌── MAIN world CS ─┐  window   │ ┌───────────────────────── isolated CS ───────────┴───────────────────┐ │
│ error capture    │ messenger │ │ data hub: serialize HTML on DOMContentLoaded → headers → notify     │ │
│ (regex extract,  ├───────────┼─▶ devtools; eager single-flight pass; serve FDT/detections/diagnoser │ │
│  dedupe, cap 50) │ (validated│ │ known-conflicts UI (shadow root); side-by-side UI (shadow root);    │ │
└──────────────────┘  batches) │ │ improvements (D-bugger menu entry); on-page inspector strip (opt-in,│ │
                               │ │ shadow root); live-test executors (RUCSS tester, beacon harness,    │ │
                               │ │ LCP analysis, script runtime view) triggered via panel/strip        │ │
                               └──────────▲──────────────────▲──────────────────────────────────────┘ │
                                          │ tab messaging    │
                    ┌─────────────────────┴───┐   ┌──────────┴─────────┐   ┌──────────────────────┐
                    │ devtools page → panel   │   │ popup (active tab) │   │ options (sync store) │
                    │ onSearch next/prev push │   │ toggles + apply    │   │ improvements         │
                    │ Elements sidebar pane   │   │ Diagnoser params   │   └──────────────────────┘
                    └─────────────────────────┘   └────────────────────┘
   exclusion-builder (unlisted page): pure lib/exclusions engine + FSA file IO (+ FF fallback)
```

Rules baked into this architecture:

- **The content script never holds page-derived state that outlives its context** — every listener/observer registers through `ContentScriptContext` and cleans up via `ctx.onInvalidated`.
- **Everything crossing a boundary is validated** (message payloads, storage reads, KC DB entries, error words) by unit-tested guards in the owning module.
- **Heavy work is lazy where it still pays:** the detection pass runs eagerly at capture — one single-flight pass whose results panel requests read as cache hits (owner decision 2026-10-08: the toolbar badge and the timing log must work with no panel open); `jsonrepair` and shiki load via dynamic import; virtualization kicks in past 100 rows.
- **No embedded 45 KB JSON in content scripts** (KC DB is owned by background; CS reads storage, background seeds it if empty).

## 4. Cross-cutting conventions (enforced in every phase)

1. **TSDoc everywhere, `why` over `what`** — per AGENTS.md; no JSDoc types in `.ts`.
2. **Strict types, no `any`** — legacy's `DiagnoserData = { noRocketData: any }` becomes a real discriminated type in P1 (verified against the diagnoser plugin's JSON shape; unknown fields stay `unknown` and are narrowed at render).
3. **Solid, not React** — no destructured props; components run once; `createMemo` for derived lists; `For`/`Show`/`Dynamic`.
4. **Error model** — "couldn't run at all" throws typed errors (e.g. `InvalidExclusionError`); "operation failed" returns a result the UI branches on; every `browser.*` call checks rejections; best-effort side work (e.g. devtools notify) never masks primary failures.
5. **Validation helpers** are per-module pure functions with tests — no schema library in content-script bundles.
6. **Naming** — ports keep user-facing strings identical unless listed as an enhancement (e.g. "Excluded by FDT legacy" → "Excluded by FDT"); internal names follow WXT layout above.
7. **Logging** — single `lib/logger` prefix `[WPR FDT]`; page-processing keeps a timing log (new format, see §1.3) so manual comparisons stay possible; no logging of page content or sensitive data.
8. **Commit / docs** — Conventional Commits; AGENTS.md updated whenever a phase adds scripts, deps, permissions, or surfaces (each phase file lists exactly which updates).
9. **One declaring site** — every constant, data table, regex/selector, type, and helper is declared once in its owning module and imported everywhere else; re-typing a value under a second name is a defect, not a pattern (the legacy engine duplicated `DELAYJS_SRC`/`LAZYLOAD_EXCLUSIONS_LIST` locally, and the port's reference engine briefly repeated the same smell — see P1's shipped deltas). The test-only reference engine is the one sanctioned duplicate, and only for control flow: it imports the shared vocabulary (`lib/wp-rocket/constants`) and contract types (`lib/wp-rocket/types`, type-only) so the parity harness compares independent logic over one shared vocabulary.
10. **Ports reshape, never mirror** — source structures (type shapes, module layout, naming) are reworked into the port's intent-revealing shape when ported; only behavior and user-facing strings stay identical (see AGENTS.md, "Never port structures as-is").
11. **Design bar is uniform.** UX studies happen at design time (P5 owns the committed study; phases consuming it trace to it rather than redesign ad hoc); every page-facing UI is shadow-isolated per AGENTS.md; all surfaces share one design language (P0 tokens incl. the status/attention vocabulary; one appearance model — `system` default / `dark` / `light`, applied before render on every surface per AGENTS.md's UI-themes rule), and 'better UI' claims carry the mechanical gates in P11's/15's checklists (axe AA, token-pair contrast, reduced-motion, isolation audit). **The concrete bar — layout/breakpoints, motion values, states, keyboard, contrast, performance, copy and the per-change DoD — is declared once in [`../ui-ux-bar.md`](../ui-ux-bar.md) (owner mandate 2026-10-14) and binds every UI phase; phase docs cite its rule ids.**
12. **Plugin-native naming.** Every rendered string — cards, chips, subtitles, report lines, strip text, popup toggle labels, options rows — names features exactly as the plugin settings UI and its knowledge base do. The tool's invented abbreviations (ATFO, OCI, ALR, LRC, DJE, RUCSS, CPCSS, SHGF, …) are code-internal identifiers only and are never rendered; detection-row keys mirror the plugin's own option/filter/meta identifiers. Verified KB spellings (2026-10-07, the beacon/Priority-Elements work):

## 5. Verification methodology (applies to all phases)

1. **Fixture corpus (P1):** capture real-world HTML from WP Rocket test sites (cached, uncached, `?nowprocket`, DelayJS old/new type variants, ALR, minify, CPCSS, PSI pages) into `lib/detection/fixtures/`. The 13 detection functions run against every fixture in tests; snapshots pin behavior; the port's output must match legacy's algorithm on the corpus (a one-off, test-only reference harness — never shipped; it reimplements the reference algorithm, and its legacy provenance stays in this section and the P1 doc, never in its code or comments — no-legacy rule, AGENTS.md).
2. **Side-by-side extension comparison:** load legacy build + new build together; on each fixture page assert identical detections (script lists, counts, versions, headers-derived cards) and compare the timing logs.
3. **Manual checklists per phase** (each phase file) including Firefox spot-checks for every phase touching content scripts or file APIs (`pnpm dev:firefox`).
4. **Budget checks:** after each producer/consumer phase, `pnpm build` + measure `du -k` per surface against §1.3; regressions block the phase.
5. **Security pass per phase:** enumerate every new boundary (message type, storage key, DOM injection) and confirm a validator exists + is tested.
6. **Improvement enforcement (how "better than legacy" is made fail-able):** the headline claims are not aspirations — each has a mechanism that can fail:
   - **Speed (≥ 30 % median):** automated bench harness (`pnpm bench:detection`, P1) times the port engine against the test-only reference implementation over the whole fixture corpus and asserts the ratio; a scripted real-page protocol (P15) cross-checks in a real browser.
   - **Size:** `pnpm check:budgets` (P0) measures every built surface (raw + gzip) against the §1.3 table and exits non-zero on breach; each building phase runs it (its checklist names the surfaces it owns).
   - **Dependency bans:** eslint `no-restricted-imports` blocks `framer-motion`/`wouter`/`react-hot-toast`/`react-syntax-highlighter` (P0); P15 diffs `pnpm ls --depth 0` against the §1.4 stack table.
   - **Test coverage:** vitest coverage thresholds on `lib/**` + `utils/**` fail `pnpm test` below the bar (P0).
   - **UI:** axe 0-violations, keyboard-only checklists, automated long-task gate on a committed 5,000-row fixture (P6), grep gates for motion-token and palette-token usage (+ P15); injected-UI isolation audit (shadow-root only, no un-scoped CSS — hostile-CSS host page, P12/P15) and design-brief conformance pass for the strip (P5H brief → P12 implementation).
   - **Per-phase enhancements:** P15 re-audits every phase's _Explicit enhancements_ list item-by-item (DELIVERED / DEFERRED / DROPPED + evidence) — a phase cannot pass having shipped parity-only work silently.
7. **CI (P0):** a GitHub Actions workflow runs the whole gate set (`compile`/`lint`/`format:check`/`test`/`build`/`check:budgets`; `build:firefox` added in P15) on every PR and push to main — the gates are enforced machine-side, not only locally. The speed bench stays local (its ratio assertion is machine-relative and would flake on shared runners).
