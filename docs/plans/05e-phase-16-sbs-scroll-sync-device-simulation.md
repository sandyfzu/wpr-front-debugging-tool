# Phase 16 — Side-by-Side scroll sync & mobile simulation

**Depends on:** P1 (contracts), P2 + P3 + P4 (the surfaces it extends — all implemented), P0 (manifest discipline). **Effort:** M. **Parallelizable with:** nothing in its slot; internally features A and B are independent and may land in either order. **Runs:** after P4.3, before the panel phases (owner decision 2026-10-08 — the slot right after the browser-test track). **Suites:** P16.1 (rides the P4.1 harness + P4.2 site).

> **Self-contained feature phase.** Every fact, design and task lives in this file. It is numbered P16 but positioned in execution between P4.3 and P5 (hence the 05e/05f file names — insertion position, not phase position). Both features are owner-requested additions (2026-10-08): new capability, no surface behavior to mirror — the verified-facts and verification-methodology rules still apply, adapted to "verify the mechanism, not a reference build".

## Goal (plain language)

1. **Side-by-Side scroll sync.** The compare overlay gains synced scrolling: **on by default** (owner decision 2026-10-11 — planned default was off), a toggle **in the overlay's own header**, and when active, scrolling one half moves the other to the same part of its page — **mapped proportionally**, because the two copies regularly differ in height (a cached copy vs its `?nowprocket=1` twin; device variants diverge more).
2. **Mobile simulation, per tab.** A debugging state on the current tab: its requests carry a mobile `User-Agent`, and while the state is on, the page world's `navigator.userAgent` matches it. After a reload the server answers the phone question — WP Rocket's separate-mobile-cache branch becomes observable in place, and every surface (badge, overlay chip, popup row) can say why what is being seen looks the way it does. Desktop-vs-mobile comparisons run across two tabs (the pattern the PSI flow already establishes); inside one overlay both halves inherit the same tab rule, and the overlay says so.

**Deliberately not simulated** (scoped honesty): viewport, touch input, device pixel ratio, form factor, user-agent client hints — only the UA identity, server-side (the request header, which is what the plugin's server-side mobile decision reads) and in-page (`navigator.userAgent`). A wrong-viewport mobile bug is a different ticket and stays visible as such. (Scope of the superseded per-tab design — the shipped comparison presents one device's viewport inside the overlay halves; see 05g.)

## Feature A — Side-by-Side scroll sync

### Design

- [x] **Setting:** `features.sbsScrollSync: boolean` — additive key in the existing `StoredOptions` shape (`lib/storage/options.ts`, the table that already owns `features.toolbarBadge`), default **true** (owner decision 2026-10-11 — planned default was off); the chosen value persists across pages and sessions via the sync options store.
- [x] **Toggle:** a header-bar switch in the overlay (`entrypoints/isolated.content/side-by-side/`, plain Solid + P0 tokens like the rest of the overlay). A real labelled, keyboard-operable control — no animation to gate under reduced motion. Clicking applies **live**: it switches the sync engine for the open overlay on/off and writes the setting; an overlay reads the persisted value when it opens. Mid-life external changes (another surface writing the key) apply next open — stated behavior, no watcher.
- [x] **Engine (pure, tested):** `lib/side-by-side/scroll-sync.ts` — `computeSyncTarget(source: FrameScrollState, target: FrameScrollState): number | null` computes `ratio = source.y / source.range` (range = `scrollHeight − clientHeight`) and maps it onto the target's own range: `clamp(round(ratio × target.range))`. A zero-range source is never a driver (returns null); a zero-range target applies nothing; invalid inputs (NaN, negative, out-of-bounds) are refused per AGENTS.md's fail-fast rule. No DOM, no listeners, no extension APIs.
- [x] **Wiring:** the overlay attaches `scroll` listeners (wheel/drag/keyboard/touch all surface as `scroll`) to each half's `window` — same-origin halves only (see the degrade row) — through the overlay's `ContentScriptContext`. rAF-coalesced: one mapped application per scroll burst; while repositioning programmatically, a suppression flag ignores the receiving half's own scroll for that burst (no feedback loop; the next user scroll retakes driver control). Per-side refresh re-reads that half's metrics; open, close and context invalidation tear the engine down (listeners removed, flags reset); re-open honors the persisted setting like a fresh overlay.
- [x] **Honest degrades (branch, never throw):**
  - A half whose document ended up **cross-origin** (the halves are built from the page's URL and start same-origin; a site's own redirect chain is the realistic cause) exposes nothing to the driver. That half renders a small per-side "not synced (different origin)" state and scrolls independently; the toggle stays on for the remaining half. The first failed access flips the state once — no per-scroll error spam.
  - **PSI host mode:** the toggle is not rendered there. Those halves are two PageSpeed Insights analyses of the same page — no correlated structure exists to map positions onto (the same overlay already hides close/refresh on that host). Recorded reason; a structure-aware PSI sync would be a new decision, not an omission.

### Tests

- [x] `lib/side-by-side/scroll-sync.test.ts` — mapping matrix (equal ranges, differing ranges, both edge clamps, zero-range source/target, negative/NaN refusal), rounding direction pinned, suppression-window semantics (an applied position never re-triggers), refresh re-reads ranges, teardown completeness. The attach/detach/setting glue is entrypoint wiring per AGENTS.md; the engine carries all the judgment.

### Shipped (Feature A, 2026-10-11)

- **Layout:** the pure engine + burst driver live in `lib/side-by-side/scroll-sync.ts`; the DOM session (halves, listener adoption, blocked flip) lives in `entrypoints/isolated.content/side-by-side/sync-session.ts`; the overlay module wires the lifecycle. The halves' side union moved here as `CompareSide` (one declaring site — the overlay's `SideBySideOverlaySide` alias is gone).
- **Suppression window:** two animation frames long, per receiving side, token-guarded so only the newest application's clear closes it — continuous driving keeps it open, a user scroll after the burst retakes control. The driver reads both halves fresh per burst (no cached metrics — per-side refresh is absorbed for free).
- **Scroll filter:** only the half's own document scroll drives a burst (capture-phase listener at the frame window; inner scrollables are page furniture, not the compared position). Applies are `scrollTo({ behavior: 'instant' })`, so a page's `scroll-behavior: smooth` cannot glide and re-enter the window.
- **Read contract:** the adapter refuses a torn read (NaN/negative/out-of-bounds) as a transient null instead of returning garbage; the pure engine still throws on such inputs when they arrive directly (both pinned). Cross-origin access (read, apply, or the listener attach itself) flips the per-side blocked state once per session.
- **Budget (deliberate re-derivation):** the isolated content script measured 85.1 KiB raw / 30.1 gzip (develop measured 83,509 B → branch **87,140 B**: the engine, session, switch and markers cost 3,631 B); the row moved 85/30 → **88/31** in `scripts/budgets.json` — a feature-committed raise, not a nudge.
- **Verified:** gates green; the full e2e tier green in three consecutive runs (36/36 each); a throwaway Playwright probe (run, then deleted — the permanent pin is P16.1's) exercised the real overlay: default-off switch, live apply, proportional 40 % → 40 % mapping across differing ranges, no oscillation after an application, reverse drive bottom→bottom, toggle-off stops syncing, close restores overflow, and a fresh page's overlay honors the persisted choice.
- **Deferred to its own rows:** the cross-origin degrade's permanent browser pin and the site round trip ride P16.1 (the degrade mechanics themselves were verified once through the throwaway fixture of the audit pass, below).
- **Owner decision (2026-10-11):** after testing, the default flips to **on** — `sbsScrollSync` now defaults to true (FALLBACK, validators, and the pinned shapes re-derived; the toggle still persists an explicit off). The plan-time default-off is kept visible in the Goal line as a dated note, not erased.
- **Owner-reported palette defect (2026-10-11, reproduced and fixed):** the overlay bar (and every other UI mounting through `entrypoints/isolated.content/ui/mount.ts` — including the Known Conflicts panel) rendered the LIGHT palette under a dark OS with the `system` appearance. Reproduced live: WXT's shadow-root isolation reset (`:host { all: initial !important }`) aborts the token stylesheet's `:host { color-scheme: dark }` chain, so the tree inherited `normal`, and `light-dark()` under `normal` resolves the light branch — the system leg of the injected palette had never rendered dark. Fix: the shared mount now declares the system choice on its own container (`data-theme="system"` → a new token rule pins `color-scheme: light dark`), letting the browser resolve dark/light per-element and follow live OS changes; explicit Dark/Light were already correct and stay untouched. Pinned permanently by the new `theme.spec.ts` suite (four cases incl. the real-time OS flip); extension pages were never affected (no shadow reset there).
- **Owner-reported open-path sync defect (2026-10-11, reproduced and fixed):** with the default-on setting the overlay opened with sync on but the halves never followed until a switch off/on cycle re-armed them (the switch path had always worked). Proven live by a new no-toggle e2e case run against the unfixed build (failed: the untouched half never moved). Root cause: the open path started the engine right after `ensureUi`, while the overlay's render — the thing whose ref callbacks register the frame slots — was still in flight inside the shared mount; `session.start()` marked a running driver over two empty slots, `attachHalf` attached nothing (not even the load re-adopt), and the start's idempotence guard turned every later start into a no-op: a permanently deaf session only a switch cycle revives. Default-off had never exposed it — sync started only from the switch, always with frames present. Fix: the open awaits the overlay's mount promise (slots register through its render) before starting; the session's unregistered-slot skip is no longer silent (a debug log names the side) and its start contract is pinned in the interface doc. Pinned by the mechanic suite's fourth case: open → drive one half to its bottom → the other reaches its exact mapped bottom, no switch interaction.

### Audit record (2026-10-11, Feature A adversarial pass)

Two findings, both fixed on this branch, both verified by re-run:

1. **The `features` slot broke its own seam.** `parseStoredOptions` validated the two known flags but _dropped_ any unknown key — while `improvements` carries future ids for exactly this reason — and the toggle's persist is a read-modify-write through that validator: every switch click would have erased a feature key a later version added. The slot now mirrors `improvements` (defaults seeded first, every own boolean-valued key carried, non-boolean dropped), the interface grew the matching index signature, and tests pin kept/dropped/absent behaviors. (Untyped hostile keys were never trusted — only boolean values cross.)
2. **A frame's load re-adopt was armed too late.** `attachHalf` registered the iframe-element `load` listener only inside the successful-window path, so a frame whose `contentWindow` did not exist yet could never be adopted later — a permanently dead half with no recovery path. The re-adopt is now armed before anything else; a cross-origin refusal during the window attach tears the half's re-adopt down deliberately (the blocked state is session-final, matching the flip-once rule).

Also verified in a real browser for the first time (throwaway dual-origin redirect fixture + probe, run then deleted — P16.1 owns the permanent pins): the redirected half flips to its per-side "not synced (different origin)" state exactly once through the refused re-adopt attach, with one marker, no growth on repeated scrolls, no extension console errors, a free-scrolling healthy half, and a surviving (still checked) switch; the visible label text toggles the switch like the input itself. After the fixes: gates + budgets green (isolated script 87,140 B / 30.1 gzip against the 88/31 ceilings), and the full e2e tier green in six consecutive runs — after one transient site-suite failure in the first post-fix run that matched the retry-normal pre-audit bisection family and left no report (the following runs were unaffected; P16.1's permanent pins will make any residual flake nameable).

## Feature B — Mobile simulation (per tab)

> **Superseded (owner refinement, 2026-10-11):** the shape below was refined into an **overlay-scoped mobile-comparison mode** — strictly live while the compare overlay is open (close resets the UA), real viewport presentation in the halves (one device: UA + resolution), reload both halves on every state change, PSI side-by-side untouched, no per-tab generic control. The living contract is `docs/plans/05g-phase-16-2-sbs-mobile-comparison.md`; the rows below are the superseded first design, kept for history. **Shipped as the refinement (P16.2 B1–B5, 2026-10-12; record in 05g)** — the control surface below never shipped: no menu row, no badge mark, no overlay chip, no P8 popup row.

### Design

- [ ] **Module:** `lib/device-simulation/` — self-contained: a `DeviceProfile` table (one mobile row initially — a current-generation Android Chrome UA string; extensible shape: adding a profile is a row plus its tests), pure rule derivation, state/validator shapes, all unit-tested. The shipped UA string is **verified in this phase** against the plugin's current server-side mobile decision on the P4.2 site (the P16.1 round trip is the gate; a needed correction is recorded, never assumed — modern UA reduction means the string must keep the device-class tokens the decision listens for).
- [ ] **Rule mechanism (Chromium):** one session rule per activated tab via `updateSessionRules` — `action.requestHeaders = [{ header: 'user-agent', operation: 'set', value: <profile> }]`, `condition: { tabIds: [tabId] }` (tab-scoped conditions are session-scope-only — the API fact that makes per-tab state native; verified against the Chrome docs). `set` rewrites the header outright (it is not limited to the append-only header list). The rule applies to every request of the tab — a consistent phone session including sub-frames; the Side-by-Side halves inherit it by construction.
- [ ] **State = the rules themselves.** Active state is derived by querying session rules (a deterministic rule id per tab); there is **no per-tab map in the service worker** — no SW-restart staleness, no GC-map class of bugs. Lifecycle: add on enable, remove on disable/`tabs.onRemoved`, and a belt-and-braces sweep at start (session rules only die with the browser or an extension install/update — the docs-verified lifecycle; the sweep covers reload oddities). One rule per active tab sits far inside the 5000-rule ceiling.
- [ ] **Permission:** `declarativeNetRequestWithHostAccess`, added with the why-comment. Why this variant: the base permission exists to grant allow/block access _without_ host permissions; this extension already carries broad declared host permissions, and `…WithHostAccess` performs actions only inside those host permissions **without adding an install-time warning** — the documented use case. AGENTS.md/README updated during the phase.
- [ ] **In-page identity:** a tiny colocated module in the MAIN-world entrypoint (`entrypoints/main-world/ua-identity.ts`): listens on the additive window-bridge channel and shadows `navigator.userAgent` for the duration (define/restore the original descriptor; no other navigator surface is touched; restored on revert — page navigation resets everything anyway, and the MAIN world has no invalidation context, recorded in P4). The isolated content script owns the lookup + relay (data-hub sibling module): the boot ask at document-start plus the live push below. Both bridge sides validate the payload (`parseDeviceSimState`); a spoofed channel message can only manipulate the page's own view of its own navigator — page-world self-inflicted, no path back to the server's decision; noted in TSDoc (P4's untrusted-MAIN rule reads in both directions).
  - **Accepted, recorded race:** the shadow applies when the bridge message lands (a task or few after document start) — a page script reading `navigator.userAgent` in its very first synchronous task can see the host UA. The server decision never depends on this (the request header is rewritten at the network layer for the whole request), and the suite pins that the override lands before the page's first animation frame.
- [ ] **Protocol additions (additive per P1's policy):** `getDeviceSimulation` (CS → background, no payload — the background resolves the sender tab; returns `DeviceSimState | null`) and a live push `deviceSimulationChanged` (background → tab CS on every toggle, same payload) so a running page follows the state without a reload. Validators + tests ship with the rows.
- [ ] **Control surface, shipped in this phase (before the panel exists):** the context-menu registry gains a page-scoped entry — **"Debug this tab as mobile"** — click toggles the state for the clicked tab (one row + one action arm in the existing registry; the dispatch deps gain the injected toggle hook exactly the way the database refresh already does). It is a click-toggle, not a checkbox row: menu checked-state is a _global_ item property and cannot honestly represent per-tab state; truth is shown where it lives (badge + overlay chip; the popup row gets the per-tab state naturally at P8).
- [ ] **Visible at a glance** (stated as its own task — unmarked simulation is how UA bugs get misdiagnosed): while a tab's state is on, the toolbar badge adds a **"simulated" mark** over the usual presence colors (pure-core extension of `badgeFor` + tests; cleared with the state), and the SBS overlay header shows a small "mobile simulated" chip (home recorded in P3's forward note). Capability is feature-detection at each UI (`'declarativeNetRequest' in browser`); the state itself comes from the protocol ask.
- [ ] **Popup row lands at P8** (recorded there + its suite): a row beneath the option switches, applying **immediately** via the rule mechanism — deliberately outside the Apply/Reset URL flow (different mechanism; the boundary is recorded in the popup doc), reading its per-tab state on open.
- [ ] **Firefox degrades explicitly:** DNR is not part of the shipped MV2 path — without the API, the toggle returns a typed unavailable result, the badge never lights, the chip never shows, and the popup row (P8) renders the explicit "not available in this browser" state with the documented fallback (the browser's own devtools device emulation for manual sessions). Chromium wins; Firefox is never half-working (AGENTS.md rule).
