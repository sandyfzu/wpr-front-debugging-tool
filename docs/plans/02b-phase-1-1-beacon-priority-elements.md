# Phase 1.1 — Beacon & Priority Elements detection (performance hints)

**Depends on:** P1. **Effort:** M. **Parallelizable:** none — P2–P4 consume this engine, and P11 merges the generator-meta source on top of these rows.

## Goal

Correct the detection model both baselines got wrong around WP Rocket's measurement beacon. The first baseline's engine treats beacon presence as "Optimize critical images active"; the second baseline uses the same beacon as a fallback marker for its ALR and auto-preload-fonts checks. Verified against the WP Rocket plugin source (2026-10-07), the beacon is **shared** by four features — the _Priority Elements_ / performance-hints family — and is injected when **at least one enabled feature still lacks its applied row** for the URL+device. Its presence proves none of them individually.

This phase: (1) detects the beacon as its own registry row; (2) detects each of the four beacon-backed features **independently of the beacon**, from their own applied markup and, when the beacon is present, from the per-feature `status` map in the page's inline beacon config; (3) drops the misleading `beacon` field from the Optimize-Critical-Images row; (4) adds the `preconnect_external_domains` check, which no baseline had.

Beacon facts (each verified in source):

- Markup: `<script data-name="wpr-wpr-beacon" src='…/wp-rocket/assets/js/wpr-beacon[.min].js' async></script>` preceded by the inline config `<script>var rocket_beacon_data = {…}</script>`, both injected before the last `</body>`. The `.min` suffix is dropped under `SCRIPT_DEBUG` — matching must be min-agnostic.
- Injection rule (Processor): inject iff ≥ 1 context-allowed factory has no applied DB row for (URL, device); skipped when `DONOTROCKETOPTIMIZE` (except SaaS visits) or a logged-in user with User Cache. So **beacon present = "≥ 1 enabled feature pending for this URL+device"**; once every enabled feature is applied, the beacon is gone from the cached page. Partial states are normal: applied markers for one feature can coexist with the beacon for another.
- The inline config's `status` map names exactly which features are enabled at injection time: a present `true` key (`atf` / `lrc` / `preload_fonts` / `preconnect_external_domain` — singular for preconnect, verified) = that feature's context allowed; an **absent key = feature disabled** (helper/filter/option). The config also carries `is_mobile`, `width_threshold`/`height_threshold`, `delay`, `ajax_url`, `nonce`, `url`, `debug`, and per-feature payloads: `elements` (ATF selector list), `preconnect_external_domain_elements`/`preconnect_external_domain_exclusions`, `preload_fonts_exclusions`/`processed_extensions`/`external_font_exclusions`.
- Pending can persist legitimately — direct beacon blockers: visits outside the required dimensions (mobile < 393×830, desktop > 1600×700) and headless browsers never execute it; and pending lasts longer without pre-warmup (it skips on blocked `?wpr_imagedimensions=1&nowprocket=1&no_optimize=1`, `WP_ENVIRONMENT_TYPE=local`, or a license expired > 15 days — meanwhile only organic eligible visits collect). "Beacon present" must never be presented as an error state — it is "collecting / not yet applied".
- `data-rocket-preload` is stamped only by the OCI LCP preloads and the automatic font preloads (shared attribution attribute — the existing `detectPreloadedResources` collects both; unchanged).
- Pre-3.19 manual "Preload fonts" emitted `link[rel=preload][as=font][crossorigin]` **without** `data-rocket-preload` (verified in v3.16.1 source) — it must never assert the automatic feature.
- The `<!-- wpr_* -->` feature comments are stripped from the final page when the meta generator runs (and always under white-label or for logged-in users) — comment detection is corroboration only; structural markers are primary.

## Tasks

### 1. `lib/detection/priority-elements.ts` — the beacon subsystem

- [x] `detectBeacon(page)`: `script[data-name="wpr-wpr-beacon"]` (primary anchor) OR a script `src` matching the assets path `wp-rocket/assets/js/wpr-beacon` + optional `.min` + `.js` (fallback — catches builds whose tags were mutated by other optimizers, and the `SCRIPT_DEBUG` non-minified variant). Result row `priority_elements_beacon`.
- [x] `parseBeaconConfig(page)`: find the inline script whose text matches `/^\s*var\s+rocket_beacon_data\s*=/`, JSON-parse the remainder (trailing `;` tolerated), validate at the boundary (untrusted page data): object; `status` an object whose **known** keys (`atf`, `lrc`, `preload_fonts`, `preconnect_external_domain`) must be booleans; unknown keys preserved read-only via index signature; `isMobile` boolean when present; `elements` / `preconnect_external_domain_elements` / `preconnect_external_domain_exclusions` / `preload_fonts_exclusions` / `processed_extensions` / `external_font_exclusions` parsed as capped string lists when present (support value: what the beacon was told to process). Malformed/hostile config → row degrades to `{ present: true, status: null, isMobile: null }` — never throws, never breaks the pass. Reuse the P1 `LIMITS` scale for caps.
- [x] Row shape: `priority_elements_beacon: { present: boolean; status: { atf?: boolean; lrc?: boolean; preload_fonts?: boolean; preconnect_external_domain?: boolean } & Record<string, unknown> | null; isMobile: boolean | null; …payloads }` — full field docs in `lib/wp-rocket/types.ts`.

### 2. The four feature checks — applied evidence only; pending state composes at the view model

Each check returns only what the page itself proves; "collecting (beacon)" composition happens in the view model (P6/P11 render) from the beacon row's `status` map — the engine stays evidence-pure:

- [x] **`rocket_above_the_fold_optimization` (Optimize critical images) — reshape.** Drop the `beacon` boolean (moved to the beacon row; pure duplication under the corrected model). Keep `present` + `preloadedImages: string[]` (parity anchors — counts and URL lists identical to the P1 engine's collections; enriching entries to `{href, imagesrcset, imagesizes}` objects is a P6 view-model option, not an engine contract change). Applied verdict: ≥ 1 `link[data-rocket-preload][as=image]` — **including when the beacon is present** (the P1-pinned "beacon wins over the image list entirely" behavior is exactly the conflation: it hides applied evidence on partial pages, so it is dropped and replaced by a mixed-state fixture). Add `lcpComment: boolean` — the trailing `<!-- wpr_oci -->` feature comment (corroboration only: stripped when the meta generator runs; `img[fetchpriority=high]` alone proves nothing — it is a standard attribute third parties set).
- [x] **`automatic_lazy_rendering` (new row; Automatic Lazy Rendering).** `{ present, lazyRenderElements, inlineCssPresent, locationHashes }`: applied verdict = ≥ 1 `[data-wpr-lazyrender]` (the inline style id corroborates — it is added iff ≥ 1 element converted); `locationHashes` = `[data-rocket-location-hash]` count, which the plugin stamps on every render while LRC is enabled and strips on apply/bypass — collecting-phase evidence. Hashes alone → `present: false`, the count still reported for the view model's "collecting" state.
- [x] **`auto_preload_fonts` (new row; Preload fonts).** `{ present, fonts: string[] }`: `link[rel=preload][as=font][data-rocket-preload]` hrefs. The attribution attribute is what separates the automatic feature from pre-3.19 manual font preloads and third-party font preloads (same markup, no attribute). Known overlap recorded: the emitter is shared with RUCSS's opt-in fonts-preload path (`rocket_enable_rucss_fonts_preload`, default off — verified in `UsedCSS.php`, which the plugin disables when the automatic feature is allowed) — the footprint alone proves "WP Rocket preloaded this font", while `status.preload_fonts` (beacon config) / the meta key attribute the Media-tab feature specifically.
- [x] **`preconnect_external_domains` (new row; Preconnect to external domains).** `{ present, domains: string[], preconnectCount: number }`: union of `link[data-rocket-prefetch]` (dns-prefetch) and `link[data-rocket-preconnect]` (preconnect) hrefs + the count of the preconnect variant. Attribution attributes only — a bare dns-prefetch hint (e.g. the `.rocketcdn.me` hint the `rocket_cdn` check matches) asserts nothing here; if a RocketCDN hint carries the attribution attribute, both rows fire (different features — accepted, verified on-site in the checklist).
- [x] **`wpr.present` propagation** gains the beacon row (and the three new feature rows): a beacon-only page — features pending, zero applied markers anywhere — must surface WP Rocket as present (legacy rendered `wpr.present = false` there). The parity propagation rule stays "every check except `wpr` and `defer_all_js`"; the beacon row joins that set deliberately (detection correctness, pinned by a test).

## Shipped deltas (vs the plan text above)

- **Config `elements` is a comma-joined STRING, not a list** (verified in the plugin's `add_custom_data`: `implode(', ', …)`). The plan assumed a capped string list; the engine carries the string verbatim (cap 4096) instead of re-shaping plugin output — the four real array payloads (`BEACON_CONFIG_LIST_FIELDS`) are the capped lists.
- **The config parse feeds the beacon row only.** None of the four feature checks consume it (their rows carry page-markup evidence only; pending composition is view-model work), so passing it to them would be a speculative API — the orchestrator parses once and `detectBeacon` merges it.
- **The config parse also accepts a JavaScript object literal** (post-audit, 2026-10-07). The plan's spec (JSON after the assignment, trailing `;` tolerated) degrades on every page whose served HTML was rewritten — the corpus itself carries three such real captures (`qa-landing-page`, `qa-elementor-overlay`, `qa-llcssbg`: prettified HTML, single-quoted JS keys/strings, expanded attributes), where the config's whole status map vanished. The plugin's own emission is strict `wp_json_encode` JSON (verified across the 3.17-pilot original → develop, and against the live 3.22-prealpha2 QA site), so JSON stays the primary path; a bounded character-wise JS-literal parser (JSON escape set in either quote style, ≤ 4 nesting levels, ≤ 2,000 values, full-input consumption, no eval and no string→JSON regex transforms) is the fallback, implemented independently in both engines so parity holds. The three fixtures now pin the fallback path with populated configs. Empirical correction found while testing it: sticky (`y`) regexes with an additional `^` anchor only ever match at position 0 — the parser's number/bare-key regexes carry no `^`.
- **Beacon-config caps are single-sourced in `lib/wp-rocket/constants.ts` (`BEACON_CONFIG_LIMITS`)**, not in `validate.ts`'s `LIMITS`: both engines import them, and the test-only reference engine may import only that module (the eslint guard on `lib/detection/reference/**`) — so the parity harness compares identical caps. Status-map rules (known keys boolean, unknown keys preserved only as bounded JSON primitives — strings/finite numbers/booleans/null; anything structured degrades; own `__proto__` keys always degrade — assigning through the name would invoke the inherited setter, and a `null` value would clear the rebuilt object's prototype) are documented there too and enforced identically in the engine parse, the reference parse, and the boundary validator.
- **Feature-comment collection trims.** The plugin writes `<!-- wpr_oci -->` — the padding spaces are part of the comment data, so the collected id is the trimmed form (`FEATURE_COMMENT_PATTERN` over comment data, trimmed push, capped at 256; real pages carry ≤ 10). Verified against the plugin source: comments are appended after `</html>` by `CommentTrait` (data `wpr_<feature>`); the corpus's real pages carry them only inside the generator meta's `data-wpr-features` attribute (the meta generator strips the comments — P11's source), so the corpus's collected comment lists are empty and `lcpComment` fires on the crafted fixtures only.
- **Resolved-href semantics for the new lists** (fonts/domains): `link.href` properties — relative URLs resolve and bare origins normalize with a trailing slash, matching the P1 list contracts and the plugin's `esc_url` emission. Empty hrefs prove no domain/URL and are dropped from the lists (the preconnect VARIANT count still counts them — a variant link exists on the page even when its href is broken).
- **`preconnect_external_domains` union dedupes by first occurrence** (a domain hinted by both variants appears once; `preconnectCount` counts variant links regardless).
- **The four new rows sit between `rocket_above_the_fold_optimization` and `minify_css` in registry order** (four feature rows, then the family's shared beacon row) — output key order mirrors the reference engine, so serialized payloads stay shape-for-shape comparable.
- **Corpus grows by 9 crafted fixtures** (two pending variants — with/without the fonts status key; applied-oci with all five LCP-preload variants; applied-lrc/-fonts/-preconnect; collecting-lrc; mixed-partial; adversarial) — 23 fixtures total, parity 0 diffs.
- **`isRecord` promoted to `utils/is-record.ts`** (second instance of the concept — the validator's private guard is now shared), imported by `validate.ts` and the subsystem.
- **Verified plugin-source nuances recorded for consumers:** the preconnect controller sets `status.preconnect_external_domain: false` EXPLICITLY when disallowed while the fonts controller OMITS its key — both mean "not enabled here"; `status.atf`/`status.lrc` are always present (true/false). Absent = the factory never ran. Consumers must treat absent and `false` alike.

## Adversarial audit (2026-10-07, shipped with the phase)

Post-implementation audit with empirical probes (each finding fixed immediately, then pinned as a regression test):

- **Real-world config shape missed (the significant catch).** The plan's JSON-only parse degraded the entire config on any served page whose HTML a tool rewrote — 3 of the corpus's own 23 fixtures. Fixed by the JS-literal fallback above; the fixtures that exposed it now pin the fixed behavior.
- **Engine output broke the messaging boundary on srcset-only preloads (P1-era latent bug, caught by the new contract test).** `parsePreloadedResources` required a non-empty `href`, while the engines legitimately emit `href: ''` for a srcset-only preload hint — the full panel payload would have failed `parseFdtData` and shown an error state. Fixed (empty rows accepted, matching the delay-row empty-`src`/`content` precedent), and the seam is now permanently pinned by `lib/detection/contract.test.ts`: BOTH parsers (`parseWprDetections` and `parseFdtData`) accept every fixture's actual `runDetection` output — an engine change that stops parsing is a release blocker, not a panel surprise.
- **Sticky-regex anchor bug.** `^` combined with the `y` flag makes a sticky regex match only at position 0; the literal parser's first implementation silently failed on every number and bare key after offset 0 (the initial unit fixtures survived because they had none). Found empirically, fixed in both engines, covered by the literal-shape tests (which parse configs full of numbers).
- **`__proto__` passthrough.** An own `__proto__` key inside `status` (JSON.parse materializes one) was silently dropped for primitive values — and a `null` value actually cleared the rebuilt object's prototype via the inherited setter. Engine, reference and validator now reject it explicitly (hostile → degrade/reject, pinned).
- **Unbounded pre-parse JSON materialization.** A hostile config script could force a multi-megabyte `JSON.parse` before any field cap applied. The config TEXT is now capped (`BEACON_CONFIG_LIMITS.text`, 64 KiB) before parsing — a 5 MB probe rejects in ~1 ms; both engines, pinned.
- **Uncapped version strings.** A 2,000-mutation deterministic fuzz over the payload guards found `wpr.version` and `delay_js.version` accepted forged empty/oversized strings (the engines never emit either — `extractWprVersion` and the delay pattern cannot produce them). Both rows now require null or a 1–64 char string (`LIMITS.versions`); the fuzz is kept as `lib/messaging/fuzz.test.ts` (2,000 hostile mutations, 0 throws, deterministic seed).
- **Boundary arms left untested** (isMobile type, `elements` as array at the row level, degraded-config-with-payload inconsistency, `__proto__` over messaging, first-match-wins config, hostile-first config) — all verified rejecting empirically, then pinned.
- **Comment-walk cost.** `parsePage`'s new TreeWalker measured at ≈ 0.22 ms on the biggest fixture (~2 % of parse) — recorded above with the bench numbers.

**Browser-suite pointer (P4.1):** the beacon-backed detection rows are exercised end-to-end (real browser, real page pass, real capture) through the fixture corpus served by the harness — the marked fixture in `tests/e2e/fixtures/pipeline/markers.html` plus the assertion surfaces in `tests/e2e/suites/processed-page-pipeline.spec.ts` (mandated log + badge summary push rendered from the same single-flight pass this phase introduced).
