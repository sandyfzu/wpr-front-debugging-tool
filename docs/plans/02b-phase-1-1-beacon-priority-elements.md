# Phase 1.1 — Beacon & Priority Elements detection (performance hints)

**Depends on:** P1. **Effort:** M. **Parallelizable:** none — P2–P4 consume this engine, and P11 merges the generator-meta source on top of these rows.

## Goal

Correct the detection model both baselines got wrong around WP Rocket's measurement beacon. The first baseline's engine treats beacon presence as "Optimize critical images active"; the second baseline uses the same beacon as a fallback marker for its ALR and auto-preload-fonts checks. Verified against the WP Rocket plugin source (2026-10-07), the beacon is **shared** by four features — the _Priority Elements_ / performance-hints family — and is injected when **at least one enabled feature still lacks its applied row** for the URL+device. Its presence proves none of them individually.

This phase: (1) detects the beacon as its own registry row; (2) detects each of the four beacon-backed features **independently of the beacon**, from their own applied markup and, when the beacon is present, from the per-feature `status` map in the page's inline beacon config; (3) drops the misleading `beacon` field from the Optimize-Critical-Images row; (4) adds the `preconnect_external_domains` check, which no baseline had.

Beacon facts (each verified in source):

- Markup: `<script data-name="wpr-wpr-beacon" src='…/wp-rocket/assets/js/wpr-beacon[.min].js' async></script>` preceded by the inline config `<script>var rocket_beacon_data = {…}</script>`, both injected before the last `</body>`. The `.min` suffix is dropped under `SCRIPT_DEBUG` — matching must be min-agnostic.
- Injection rule (Processor): inject iff ≥ 1 context-allowed factory has no applied DB row for (URL, device); skipped when `DONOTROCKETOPTIMIZE` (except SaaS visits) or a logged-in user with User Cache. So **beacon present = "≥ 1 enabled feature pending for this URL+device"**; once every enabled feature is applied, the beacon is gone from the cached page. Partial states are normal: applied markers for one feature can coexist with the beacon for another.
- The inline config's `status` map names exactly which features are enabled at injection time: a present `true` key (`atf` / `lrc` / `preload_fonts` / `preconnect_external_domain` — singular for preconnect, verified) = that feature's context allowed; an **absent key = feature disabled** (helper/filter/option). The config also carries `is_mobile`, `width_threshold`/`height_threshold`, `delay`, `ajax_url`, `nonce`, `url`, `debug`, and per-feature payloads: `elements` (ATF selector list), `preconnect_external_domain_elements`/`preconnect_external_domain_exclusions`, `preload_fonts_exclusions`/`processed_extensions`/`external_font_exclusions`.
- Pending can persist legitimately — direct beacon blockers: visits outside the required dimensions (mobile < 393×830, desktop > 1600×700) and headless browsers never execute it; and pending lasts longer without pre-warmup (it skips on blocked `?wpr_imagedimensions=1&nowprocket=1&no_optimize=1`, `WP_ENVIRONMENT_TYPE=local`, or a license expired > 15 days — meanwhile only organic eligible visits collect). "Beacon present" must never be presented as an error state — it is "collecting / not yet applied".
- `data-rocket-preload` is stamped only by the OCI LCP preloads and the automatic font preloads (shared attribution attribute — the existing `detectPreloadedResources` collects both; unchanged).
- Pre-3.19 manual "Preload fonts" emitted `link[rel=preload][as=font][crossorigin]` **without** `data-rocket-preload` (verified in v3.16.1 source) — it must never assert the automatic feature.
- The `<!-- wpr_* -->` feature comments are stripped from the final page when the meta generator runs (and always under white-label or for logged-in users) — comment detection is corroboration only; structural markers are primary.

## Tasks

### 1. `lib/detection/priority-elements.ts` — the beacon subsystem

- [ ] `detectBeacon(page)`: `script[data-name="wpr-wpr-beacon"]` (primary anchor) OR a script `src` matching the assets path `wp-rocket/assets/js/wpr-beacon` + optional `.min` + `.js` (fallback — catches builds whose tags were mutated by other optimizers, and the `SCRIPT_DEBUG` non-minified variant). Result row `priority_elements_beacon`.
- [ ] `parseBeaconConfig(page)`: find the inline script whose text matches `/^\s*var\s+rocket_beacon_data\s*=/`, JSON-parse the remainder (trailing `;` tolerated), validate at the boundary (untrusted page data): object; `status` an object whose **known** keys (`atf`, `lrc`, `preload_fonts`, `preconnect_external_domain`) must be booleans; unknown keys preserved read-only via index signature; `isMobile` boolean when present; `elements` / `preconnect_external_domain_elements` / `preconnect_external_domain_exclusions` / `preload_fonts_exclusions` / `processed_extensions` / `external_font_exclusions` parsed as capped string lists when present (support value: what the beacon was told to process). Malformed/hostile config → row degrades to `{ present: true, status: null, isMobile: null }` — never throws, never breaks the pass. Reuse the P1 `LIMITS` scale for caps.
- [ ] Row shape: `priority_elements_beacon: { present: boolean; status: { atf?: boolean; lrc?: boolean; preload_fonts?: boolean; preconnect_external_domain?: boolean } & Record<string, unknown> | null; isMobile: boolean | null; …payloads }` — full field docs in `lib/wp-rocket/types.ts`.

### 2. The four feature checks — applied evidence only; pending state composes at the view model

Each check returns only what the page itself proves; "collecting (beacon)" composition happens in the view model (P6/P11 render) from the beacon row's `status` map — the engine stays evidence-pure:

- [ ] **`rocket_above_the_fold_optimization` (Optimize critical images) — reshape.** Drop the `beacon` boolean (moved to the beacon row; pure duplication under the corrected model). Keep `present` + `preloadedImages: string[]` (parity anchors — counts and URL lists identical to the P1 engine's collections; enriching entries to `{href, imagesrcset, imagesizes}` objects is a P6 view-model option, not an engine contract change). Applied verdict: ≥ 1 `link[data-rocket-preload][as=image]` — **including when the beacon is present** (the P1-pinned "beacon wins over the image list entirely" behavior is exactly the conflation: it hides applied evidence on partial pages, so it is dropped and replaced by a mixed-state fixture). Add `lcpComment: boolean` — the trailing `<!-- wpr_oci -->` feature comment (corroboration only: stripped when the meta generator runs; `img[fetchpriority=high]` alone proves nothing — it is a standard attribute third parties set).
- [ ] **`automatic_lazy_rendering` (new row; Automatic Lazy Rendering).** `{ present, lazyRenderElements, inlineCssPresent, locationHashes }`: applied verdict = ≥ 1 `[data-wpr-lazyrender]` (the inline style id corroborates — it is added iff ≥ 1 element converted); `locationHashes` = `[data-rocket-location-hash]` count, which the plugin stamps on every render while LRC is enabled and strips on apply/bypass — collecting-phase evidence. Hashes alone → `present: false`, the count still reported for the view model's "collecting" state.
- [ ] **`auto_preload_fonts` (new row; Preload fonts).** `{ present, fonts: string[] }`: `link[rel=preload][as=font][data-rocket-preload]` hrefs. The attribution attribute is what separates the automatic feature from pre-3.19 manual font preloads and third-party font preloads (same markup, no attribute). Known overlap recorded: the emitter is shared with RUCSS's opt-in fonts-preload path (`rocket_enable_rucss_fonts_preload`, default off — verified in `UsedCSS.php`, which the plugin disables when the automatic feature is allowed) — the footprint alone proves "WP Rocket preloaded this font", while `status.preload_fonts` (beacon config) / the meta key attribute the Media-tab feature specifically.
- [ ] **`preconnect_external_domains` (new row; Preconnect to external domains).** `{ present, domains: string[], preconnectCount: number }`: union of `link[data-rocket-prefetch]` (dns-prefetch) and `link[data-rocket-preconnect]` (preconnect) hrefs + the count of the preconnect variant. Attribution attributes only — a bare dns-prefetch hint (e.g. the `.rocketcdn.me` hint the `rocket_cdn` check matches) asserts nothing here; if a RocketCDN hint carries the attribution attribute, both rows fire (different features — accepted, verified on-site in the checklist).
- [ ] **`wpr.present` propagation** gains the beacon row (and the three new feature rows): a beacon-only page — features pending, zero applied markers anywhere — must surface WP Rocket as present (legacy rendered `wpr.present = false` there). The parity propagation rule stays "every check except `wpr` and `defer_all_js`"; the beacon row joins that set deliberately (detection correctness, pinned by a test).

## Explicit enhancements over both baselines

- Dedicated beacon row with the per-feature `status` breakdown — neither baseline surfaced it (one used the beacon as a verdict, the other as a fallback marker).
- `preconnect_external_domains` check — new; both baselines predate WP Rocket 3.19.
- Lifecycle-honest states (applied / collecting / not detected), including the ineligible-visit nuance — neither baseline distinguished "collecting" from "applied".
- Min-agnostic, attribute-anchored beacon matching (the second baseline matched `wpr-beacon.min.js` only — SCRIPT_DEBUG builds were invisible to it).
- `wpr.present` propagation includes the beacon row — beacon-only pages stop rendering as "WP Rocket absent" (badge + Detections page).
- Beacon-config payload lists (`elements`, exclusions, processed extensions) surfaced read-only — support value when diagnosing why a feature "sees" fewer elements than expected.
