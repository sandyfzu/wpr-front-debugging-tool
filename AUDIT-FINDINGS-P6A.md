### P2 (correctness / robustness)

- **P2-1 — Long-name clipping can emit duplicate names (violates the `PageCookies` doc "Unique cookie names").**
  Evidence: `lib/wp-rocket/cookies.ts:57-59` — for a name over `COOKIE_NAME_LIMITS.name`, the code pushes `name.slice(0, cap)` but marks the **full** name as seen. Two distinct over-cap names sharing the first 512 chars therefore each pass the `seen` check and emit **the same clipped string twice**, and `parsePageCookies` accepts duplicates (no uniqueness check). Repro (probe, since deleted — inlined here):

  ```ts
  sampleCookieNames(`${'n'.repeat(513)}A=1; ${'n'.repeat(513)}B=2`);
  // observed: [ 'n'.repeat(512), 'n'.repeat(512) ] — duplicates, validator accepts
  ```

  Expected per the type doc (`lib/wp-rocket/types.ts` `PageCookies.names`: "Unique cookie names"): duplicates impossible or deduped. Reachability: honest pages cannot hit it (browser cookie caps); a hostile _string_ passed to the pure function can. Not security — availability/doc-contract only.

  > **RESOLVED — `e02820a`.** `sampleCookieNames` clips before deduping, so the emitted (clipped) name is the dedupe key (first occurrence wins), and `parsePageCookies` rejects a duplicated list as a unit — the doc's uniqueness claim now holds in both directions. Reproduced first: the probe string emitted the duplicate pair red; green after the fix. Pins: `cookies.test.ts` › `two over-cap names sharing a clip emit that clipped name once (uniqueness)` + `adversarial corpus: every emission list is unique (the contract invariant)`; `validate.test.ts` › `rejects a payload with duplicate names (the unique-names contract)` + the `parsePageCookies — capture-side ↔ validator consistency` suite (every emission over the hostile corpus validates whole).

- **P2-2 — `capturedAt` accepts non-representable stamps at the boundary.**
  Evidence: `lib/messaging/validate.ts:177` — `Number.isInteger` + `>= 0` only; **9_000_000_000_000_000 and 1e21 pass** (observed in probes S10/S11). This is inconsistent with the standing defense for the page-derived cache stamp (`isRepresentableCacheStamp` in `lib/detection/describe.ts`, which caps at ±8.64e15 ms so `new Date(...).toISOString()` can never throw). P6F's "captured-at" rendering (or any relative-age math) will need its own representability guard, or the boundary should carry the cap. "As of" honesty: today the value is pass-through, clamped by nobody.

  > **RESOLVED — `e02820a`.** The boundary carries the cap, reusing the same declared constant the cache-stamp defense uses — `MAX_REPRESENTABLE_MS`, now exported from `lib/detection/describe.ts` (one declaring site; no second limit). Reproduced first: both shapes rejected red; green after. Pins: `validate.test.ts` › `caps the capture stamp at the platform representable-instant ceiling` (both repro shapes so, plus the acceptance band — 0 / a wall-clock stamp / exactly the ceiling in; one tick past and a fraction out) and the rationale line in `parsePageCookies`' TSDoc + the `PageCookies.capturedAt` doc.

  > **RESOLVED — `e02820a`, recorded honestly.** The case is genuinely impossible per the standing pattern: the getter has no throwing path (WHATWG DOM), so the one-line rationale now lives in the code beside the read it guards — the discipline's guard comment, not a `try`.

  > **RESOLVED — `5022972`.** The test states its type-only merit in name and comment (the `expect` is a declared liveness witness), and the loader gained the real runtime probe of the seam's optional `type` field the no-op leg hinted at: a resource without one is skipped, like any non-script type.

5. Regex: no metacharacter word can inject alternation, anchors, or quantifiers; `(var|let)` searches the literal only; the literal forms still match as assignment targets; every special character word builds; empty inputs answer `[]`; word order preserved; sentinel word answered empty.
