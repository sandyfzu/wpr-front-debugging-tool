# Browser-test tier (Playwright, local-only)

The real-browser test tier for this extension. **Local-only by rule: never wired
into CI** (headless runners cannot host extensions — the env contract is in the
master plan's browser-test track).

```bash
pnpm test:e2e            # all suites, headless Chromium, ~4 min
E2E_HEADED=1 pnpm test:e2e   # headed windows (the debugging opt-in)
E2E_BUILD_STRICT=1 pnpm test:e2e   # refuse to auto-rebuild: fail fast with the diff instead
E2E_WORKERS=5 pnpm test:e2e        # run suites in parallel (five browsers)
pnpm exec playwright show-report tests/e2e/playwright-report   # inspect the last run's HTML report
```

## What runs

- **Playwright (latest stable) launches Chromium from the `chromium` channel with the unpacked extension preloaded** from `.output/chrome-mv3/` (`--disable-extensions-except` + `--load-extension`, the documented extension-loading path). Runs are **headless by default** — a gate run never opens windows or steals the foreground; `E2E_HEADED=1` is the debugging opt-in (real windows open and close). The channel's modern headless hosts extensions (verified against the installed build); the legacy headless shell cannot, which is why the tier launched headed-only when it was built.
- The driver omits Playwright's default `--hide-scrollbars`: scrollbar painting and
  layout must match real browsing. `scrollbars.spec.ts` checks idle thumb pixels,
  fixed hover/drag geometry, palettes, forced colors, keyboard/wheel/drag scrolling,
  shadow isolation, and the JavaScript page's real virtual list + code panes.
- **`global-setup.ts` refuses a stale build**: it fingerprints every file the
  build reads (`entrypoints/`, `components/`, `lib/`, `utils/`, `assets/`,
  `public/`, `wxt.config.ts`, `package.json`) and compares against
  `tests/e2e/.build-stamp.json` (gitignored, derived data). On a mismatch the
  harness runs `pnpm build` first (or, with `E2E_BUILD_STRICT=1`, fails fast
  printing the changed-file list).
- **`server.mjs` is the fixture webServer**: one local port (8891) is bound to
  both `http://localhost:8891/` and `http://127.0.0.1:8891/` — distinct origins,
  so cross-origin script errors and origin-tagged comparisons are real — over
  **loopback-only** sockets (`127.0.0.1` + `::1`; nothing answers on the
  machine's network interfaces). `E2E_FIXTURE_PORT` overrides the port for one
  local run — the config's health gate and the suites' origins read the same
  override — the way to keep two concurrent harness users on this machine off
  each other's servers. Fixtures
  are committed under `fixtures/`; every response is `no-store` so each reload
  is a genuine network round-trip — the one deliberate exception is
  `/__e2e/cache-evidence`, which serves `max-age=3600` freshness evidence on
  purpose (it is the fixture exercising the caching verdicts) — and the
  `__E2E_FRAME_TOKEN__` placeholder in
  any served `.html` is replaced with a fresh per-request random token (a
  fixture page can prove its body is from the latest request).
- **A second webServer boots the P4.2 dockerized WordPress site**
  (`docker/scripts/up.sh`, ready on the bootstrap's marker
  `/fdt-state/bootstrap-ready.txt`, written last each boot — a warm volume's pages
  answer mid-bootstrap; URL read from `docker/.env` — docker stays the site's single
  declaring site). A second global setup (`site-baseline-setup.ts`) then refuses a site
  whose live `/fdt/` meta is off the bootstrap baseline (a killed settings-writing run;
  fix: `up.sh`, which forces every key a matrix combination writes). It gates **every**
  run, `site-*` suites selected or not — deliberate: the site boots for every run anyway,
  one no-store request (`fdt-no-store=1`, never cached) is cheap, and one guard beats one
  per suite. An unreachable site fails it with the probe URL, the cause and the `up.sh`
  hint. The `site-*` suites run against it. A converged stack adds ~25 s; `up.sh`
  rebuilds nothing when the volumes are warm and the reuse check skips the
  boot entirely when the stack is already up.

## The SW drive plane (beyond page DOM)

Extension state that has no page-DOM presence is asserted from the **service
worker context**:

- Playwright exposes the MV3 background as a `Worker` target
  (`context.serviceWorkers()`); the driver evaluates real `chrome.*` code there
  (`tests/e2e/helpers/extension.ts`, `evaluateInWorker`). The
  `Worker.evaluate` handle stays valid across Chromium's own service-worker
  idle suspension.
- Extension messaging is driven over the protocol's wire shape: the installed
  `@webext-core/messaging` v4 sends `{ id, type, data, timestamp }` envelopes,
  so the harness sends the extension's real protocol rows (`getFdtData`
  pull-through, `openSideBySide`) from the SW to a tab without importing any
  extension bundle.
- **Menu state is probed by duplicate-create semantics.** The extension
  `contextMenus` API has no read-back (`getAll` does not exist in the
  installed Chromium; verified live) — so "entry exists exactly once" is
  observable as "creating a second item with that id is refused with the
  duplicate-id `lastError`". A scratch id outside the registry serves as the
  probe's absence control. The title/contexts/documentUrlPatterns parity
  shapes are therefore pinned by the background's own unit table
  (`entrypoints/background/context-menus.test.ts`), not re-read at runtime.

## The panel's devtools-contract data path (`helpers/panel-data.ts`)

The panel suites' ready legs ride one seam: open the fixture page first (its
tab id is resolved with the same `tabs.query` read-back the service worker
uses), then boot the panel page with `page.addInitScript` stamping exactly one
value — `devtools.inspectedWindow.tabId`, written onto both namespace objects
the extension page exposes (`window.chrome` and the separate `window.browser`
of this Chromium build; a `chrome`-only shim was empirically ignored by the
boot flight, probed 2026-10-14) — and, for the one suite that drives the
undefined-references reader (`panel-copy-exclusion`), the optional `inspect`
stub: a fixture-provided resource table + origin standing in for the two
`inspectedWindow` calls the reader enumerates resources and origin through
(`getResources`/`eval`) that a standalone panel page lacks. `onResourceAdded`
stays unserved (deliberate: the stub answers suite values only), so
`watchAddedScripts` degrades to a no-op there and the stale-scripts hint never
arms in the harness — a fact the store tolerates. Everything after that stamp
is shipped code:
the panel's boot fetch rides the tab-targeted `getFdtData` round trip over the
real content script, the boundary validators, the push channels and their
sender-tab scoping — the same shape a real DevTools window produces. Nothing
is ever injected into the panel's store; a fixture page's detection output IS
the fixture, and the assertions can read the served truth through the same
contract the panel used (a contract-genuine negative test cross-checks it).
The two-instance search pins relay one more envelope the same way, from the
service worker. Attached-devtools visuals stay the manual remainder.

## Real-site facts the site suites rely on (verified against the live stack)

- **One worker serves the whole `pnpm test:e2e` run** (per-file when
  `E2E_WORKERS` > 1): the browser profile and its state (cookies, storage,
  the extension's own caches) are shared across the consecutive files, so
  every suite declares its needed preconditions explicitly (the SBS suites
  clear the site's login cookies and run as a normal visitor; the admin
  suites log in themselves). Cookies set by any fixture page persist for
  the later suites on the same origin within a run — a suite pinning exact
  cookie-derived counts clears the context's cookies first.
- **Fresh-profile first `/fdt/` visit is cache-served** (green badge, the
  WP Rocket footprint comment + the `cached@` debug marker); WordPress-served
  pages (every uncached query) carry three `Link` header rows and lack the
  marker. Revisits revalidate and keep serving the same document, so each
  state is stable per tab.
- **Logged-in visitors get no cache and no optimization** (plain WordPress
  HTML) — the site suites that need cached truth stay anonymous.
- **The first navigation after a launch can miss the header capture**: the
  main-frame event races the service worker's first listener registration.
  The driver warms the capture with one throwaway local page after the worker
  event, so every suite's real pages capture deterministically.
- **Idle preconnected sockets must answer at once** (fixed in the stack
  2026-10-21, `docker/apache/accept-filter.conf`). Chromium keeps an unused
  socket to the site from earlier loads; with Apache's Linux default
  `AcceptFilter http data` (TCP_DEFER_ACCEPT) its container side stays in
  `SYN_RECV` behind Docker Desktop's port forwarder, and once idle ~15 s the
  next request on it stalled 6–27 s (raw Node sockets: idle ≤ 14 s 0.05 s,
  16–28 s 6.7–26.9 s; Chromium, one persistent profile, page → 18 s idle →
  `wp-login.php`: 4/8 hit the 20 s navigation timeout) — the
  `site-inspector-strip` "KC and the strip coexist" login timeout run alone.
  `AcceptFilter http none` (container side `ESTABLISHED`): raw 0.05 s at every
  idle up to the 20 s `mod_reqtimeout` close, Chromium 8/8 at 18 s and 21–45 s
  idles ≤ 0.10 s. Ruled out: `RequestReadTimeout`, fresh-connection transport.
  No harness retry was added — the cause is gone.

## Known flake class + the retry policy (recorded 2026-10-13, the P5I audit round; re-attributed 2026-10-20, the P9.1 audit round)

The site suites assert against the **live** dockerized site's real cache, and a
shared run can race it. The observed shape is now attributed precisely: an
uncached frame's **initial navigation committed mid-assertion** under
`site-side-by-side` — its `?nowprocket=1` document's slower WordPress bootstrap
landed the real commit inside the test's baseline→assert window (an
`about:blank` first commit reads the same footprint/markers as a bypassed
page, so a cached-side-only settle could not see it), advancing
`performance.timeOrigin` with zero site misbehavior — a baseline race the
suite's settle window masked under quiet runs and exposed under full-tier
load. **Hardening:** that test's settle now requires BOTH frames' real loaded
documents (their real `href`s + `readyState complete`) before any baseline is
taken. **Policy (backstop, unchanged):** on a failure of that shape, wait
~90 s and re-run the failing suite **once** — a deliberate manual retry.
Playwright's own `retries` stay `0`, so nothing ever auto-passes; a clean full
`pnpm test:e2e` run is the gate's evidence.

## Environment facts (verified against the installed tooling)

- Chromium for Testing 156.0.8078.4 via Playwright (above the manifest floor of
  145); extensions load per the Playwright extension docs.
- After `chrome.runtime.reload()`, any extension that declares content scripts
  vanishes from Chrome's extension registry and never revives in this build
  (verified; even with a trivial background). The harness's reload leg closes
  the browser and relaunches on the SAME profile — the bundle re-registers over
  persistent extension-owned browser state, asserting the checklist's actual
  question (ids survive extension reload exactly once).
- **Source-build parity runs a SECOND browser**: the parity suites boot one
  extra persistent Chromium context per worker loading the source extension's
  own unpacked build (`helpers/source-build.ts`). `E2E_SOURCE_REPO` overrides
  the source checkout (default: the sibling `wpr-front-debugging-tool-legacy`
  next to this repo's main checkout); `E2E_SOURCE_BUILD_DIR` overrides the
  unpacked build dir (default the checkout's `.output/chrome-mv3`). A missing
  checkout skips the parity suite naming the reason; a stale build (stamped
  HEAD or dirty state differs from the checkout) is rebuilt first. Concurrent
  harness users must set BOTH overrides — `E2E_FIXTURE_PORT` alone only
  separates the fixture servers; the source build dir is shared otherwise.
